# 云端文档损坏怎么处理

报错长这样：

~~~
2026-11-16 16:58 同步失败：云端文档格式异常：invalid-doc
2026-11-16 16:58 云端文档解析失败
~~~

从 v1.2.4 起，报错会带上**具体原因 + 实际结构 + 前 240 字符**，不再是光秃秃的一句话。

## 一、先看它到底坏在哪

设置页 → **5. 云端文档健康** → **检查云端文档**。

会输出：

~~~
后端：github
路径：bookmarks.json
版本：a1b2c3d…
大小：4210 字节
结构：object{schemaVersion:number,nodes:string}
可解析：否
问题：
  · nodes 不是数组（实际是 string）

—— 前 800 字符 ——
{"schemaVersion":2,"nodes":"..."
~~~

## 二、四种常见原因

### 1. 文件被别的程序覆盖了
比如把 `bookmarks.json` 当普通文件同步了、或者在 GitHub 网页上手滑提交了别的内容。
**特征**：`结构：不是合法 JSON`，preview 里可能是 HTML。

### 2. 结构不规范但数据还在
历史上某个版本写过裸数组、Map 对象、或者多包了一层 `{ok, doc}`。
**特征**：`结构：array(N)` 或 `object{...}`，但元素确实是书签节点。

### 3. 扩展版本不匹配
**特征**：报 `schemaVersion=3 高于本扩展支持的 2`。升级扩展即可，不要修文档。

### 4. 文件是空的或被截断
**特征**：`invalid-json`，preview 很短。

## 三、两条修复路径

### A. 自动归一化（优先）

设置页 → **5. 云端文档健康** → **自动归一化**

做的事：

1. 把当前云端内容**逐字节**备份到 `bcs-backup/bad-<时间戳>.json`；
2. 尝试识别结构（裸数组 / Map 对象 / 多包一层 / nodes 为 null）；
3. 归一化后带 `If-Match` 写回（有并发保护）。

能修的情况：第 2 类。修不了会明确告诉你"无法自动修复"并建议走 B。

### B. 用本机重建（最后手段）

设置页 → **5. 云端文档健康** → **用本机重建**

做的事：

1. 同样先备份原始内容；
2. 用**当前这台电脑**的书签树生成一份全新文档；
3. 覆盖云端，并把本地同步基线重置为这份新文档。

⚠️ **另一台设备上独有的书签不会保留**。所以顺序很重要：

~~~
1. 在"书签最全"的那台设备上操作
2. 或者：先在另一台设备「导出当前书签 JSON」留档
3. 确实要保留两边内容 -> 先在另一台设备点「立即同步」（它会试图合并）
   如果那台也报错，就各自导出 JSON，用「导入」逐个并进来
~~~

## 四、还有一条路：从 git 历史恢复（GitHub 后端）

GitHub 模式下每次同步都是一个 commit，比任何修复手段都可靠：

~~~bash
git log --oneline -- bookmarks.json        # 找到最后一次正常的
git show <sha> -- bookmarks.json | head    # 确认内容
~~~

然后在扩展里：设置页 → 6. 历史快照与恢复 → 选那个 commit → **合并恢复**。

这条路不会删掉当前设备上新增的书签，只把差异补回来。

## 四·五、另一种「坏」：文档能解析，但书签变成了两份

这不算格式损坏，报错也不会出现在 invalid-doc 里，但它是**更常见的真实事故**。

用「检查云端文档」会看到 可解析：是，可书签栏里每个目录都出现了两遍。

**怎么认出来**：在「8. 运行日志」里搜 duplicate-copies，或者同步时看到：

~~~
本机与云端几乎没有任何共同节点（id 重合 0%），但内容重合 100%：
这是同一批书签用了两套 id，继续同步会把云端写成一式两份。
~~~

**成因**：新设备（或清空过同步状态的同一台）第一次接入已有云端文档时，本机的
nodeId ↔ chromeId 映射表是空的，同一批书签全部拿到了**新的 nodeId**；而合并基线
base 也是空的，于是「本地全量」和「云端全量」都被判成新增，取并集就是两棵树。

v1.2.5 起有两个机制堵住它：

1. **身份对齐**（自动，同步前执行）：按「类型 + 标题 + URL + 层级」计算路径签名，
   把本机节点认领成云端的 nodeId，之后的合并就是正常三方合并，不会再翻倍；
2. **重复副本护栏**：万一仍出现「id 几乎零重合 + 内容高度重合」，同步会直接拦下并
   提示你，**不会**把翻倍结果写回云端。

### 已经翻了倍怎么办

设置页 → **5. 云端文档健康** → **按内容去重**

做的事：

1. 先把云端内容逐字节备份到 bcs-backup/bad-<时间戳>.json；
2. 按路径签名分组：**同一层级下标题与网址完全相同的副本**只保留第一份，其余打墓碑
   （墓碑不是删除，90 天内可追溯，也不会让离线设备把它复活）；
3. 写回云端并清空本地 base，下一轮同步按内容重新对齐。

安全性：只认「层级 + 标题 + URL」全同的节点。同标题同 URL 但挂在**不同文件夹**下的
两条不会被当成重复（那是用户真的想要两条）。

去重完再点一次「立即同步」即可。


## 四·六、文件内容变成了 GitHub API 的响应对象

报错长这样：

~~~
云端文档格式异常：invalid-doc（缺少 schemaVersion）
实际结构：object{name:string,path:string,sha:string,size:number,url:string,html_url:string}
~~~

这不是书签文档，而是 **GitHub Contents API 的文件元数据响应**。说明有人/某个工具
把 API 的返回值直接存进了 bookmarks.json（网页编辑、脚本误写、或别的工具操作过仓库）。

**好消息**：如果这个对象里还带着 content 字段（base64 正文），真数据就完好地躺在里面。
v1.2.6 起会自动识别并解开：

- 检测到 API 响应形状时，自动 base64 解码 content 并重新解析；
- 解出来的内容如果只是个缺 schemaVersion 的文档，也会一并补齐；
- 缺少 content 或 content 不是 JSON 时，明确告诉你缺的是什么，而不是含糊的「缺少 schemaVersion」。

所以：**直接点「按内容去重」或「自动归一化」**，能救就会救回来，救不回来会说明原因。

若确认无法救回，走「用本机重建」，或用 `bcs-backup/` 里那份备份对照。


## 四·七、「重建失败：云端已被其它设备更新（sha 不匹配）」

这条提示具有误导性。真实原因通常**不是**并发冲突，而是 v1.2.6 及更早版本的一个缺陷：

> GitHub 更新**已存在**的文件时，请求体必须携带该文件的 blob `sha`。
> 旧版「用本机重建」没有传 `sha`，GitHub 返回 `422 Invalid request. "sha" wasn't supplied`。
> 这条错误信息里含有 "sha"，被错误分类逻辑判成了并发冲突。

v1.2.7 修复：

1. 「用本机重建」现在会带上最新 `sha`；
2. 错误分类拆开：`sha` **缺失** -> `SHA_MISSING`（代码问题，不重试）；`sha` **不匹配** -> `CONFLICT`（并发，可重试）；
3. 三条强制覆盖路径（归一化 / 去重 / 重建）在遇到真的并发冲突时，会**自动重读 sha 再写**，最多 3 轮——
   因为这几步都是你已经点过确认的操作，数据保护靠前面的逐字节备份，不需要靠 sha 失败来兜底。


## 四·八、`content` 存在却解不出来：那是空壳文件

v1.2.7 会先尝试解开 GitHub 响应对象里的 `content`。如果仍然报：

~~~
这份文件的内容是 GitHub Contents API 的响应对象（含 name/path/sha/url），不是同步文档：
content 是空字符串（GitHub 对 >1MB 的文件不返回内联内容）。当前文件里没有可恢复的书签数据
~~~

说明 **云端那份文件里已经没有书签数据了**——它只是个元数据空壳。
四种编码我都实测过：

| content 形态 | 能否救回 |
|---|---|
| 标准 base64 | ✅ |
| 明文 JSON | ✅ |
| base64 带换行 | ✅ |
| 二次 base64 | ✅ |
| 空字符串 | ❌ 无数据 |
| 被截断 | ❌ 无数据 |

### 该怎么办

**首选：用本机重建**（v1.2.8 已修复其中的 sha 缺陷，可以正常工作了）

设置页 → 5. 云端文档健康 → **用本机重建** → 连点两次确认

它会：先备份云端空壳 → 用这台电脑的书签生成新文档 → 写回云端 → 重置本地基线。

**如果想找回更早的版本**：

设置页 → 6. 历史快照与恢复 → **云端快照**页签。GitHub 模式下每次同步都是一个 commit，
挑一个 `.json` 里的 `nodes` 数量正常的版本，用「合并恢复」拉回来。
（v1.2.8 起恢复路径也做了容错，坏文件不会再让恢复直接崩掉。）

### v1.2.8 在读取层做的另一层保护

`readFile` 现在会**自动透明解包**：如果云端文件内容是 API 响应对象，
读取时就把里面真正的正文取出来，上层完全无感。也就是说，只要数据还在，
同步、预览、去重、恢复都不需要你手动干预。


## 四·九、同步自动回溯 git 历史（v1.2.9）

从 v1.2.9 起，**云端当前版本读不出来时会自动去 git 历史里捞**，不需要你手动点任何按钮。

触发条件：当前 HEAD 的 `bookmarks.json` 解析失败，且后端是 GitHub。

做的事：

1. 拉取该文件的 commit 列表（最多 30 个）；
2. 从新到旧逐个用 `ref=<commit>` 读回正文并试着解析；
3. 找到第一个能解析的就采用它，日志里会写：

~~~
云端当前版本（head123）已损坏，已自动回溯到 commit c2（sync r8）并继续同步
~~~

4. 写回云端时用**那个版本的 blob sha** 做乐观锁（不是 commit sha——GitHub 要的是 blob sha），
   所以后续同步能正常覆盖那个坏版本。

也就是说：只要历史里还有一份好的，你点「立即同步」就自动好了。

只有**全部 30 个 commit 都解析不出来**时，才会退回「用本机重建」。

## 五、预防

- **不要**把 `bookmarks.json` 当普通文件放进别的同步工具（OneDrive / Dropbox / Syncthing）；
- 用 GitHub 后端时给仓库开分支保护意义不大，但可以在本地留一份 `npm run verify` 的 CI（见 docs/CI.md）；
- 定期点「立即创建快照」，本地和云端各留一份。

## 六、修好之后

点「立即同步」。如果仍然报错：

1. 再去「检查云端文档」看结构有没有变化；
2. 看「8. 运行日志」里的最后几条；
3. 最后手段：设置页 → 「重置同步基线」（不删书签，只丢弃"上次同步结果"的记忆，下次全量重新比较）。
