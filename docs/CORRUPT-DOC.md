# 云端文档损坏怎么处理

报错长这样：

~~~
2026-11-16 16:58 同步失败：云端文档格式异常：invalid-doc
2026-11-16 16:58 云端文档解析失败
~~~

从 v1.2.4 起，报错会带上**具体原因 + 实际结构 + 前 240 字符**，不再是光秃秃的一句话。

## 一、先看它到底坏在哪

设置页 → **5. 云端文档健康** → **检查云端文档**。

会输出：

~~~
后端：github
路径：bookmarks.json
版本：a1b2c3d…
大小：4210 字节
结构：object{schemaVersion:number,nodes:string}
可解析：否
问题：
  · nodes 不是数组（实际是 string）

—— 前 800 字符 ——
{"schemaVersion":2,"nodes":"..."
~~~

## 二、四种常见原因

### 1. 文件被别的程序覆盖了
比如把 `bookmarks.json` 当普通文件同步了、或者在 GitHub 网页上手滑提交了别的内容。
**特征**：`结构：不是合法 JSON`，preview 里可能是 HTML。

### 2. 结构不规范但数据还在
历史上某个版本写过裸数组、Map 对象、或者多包了一层 `{ok, doc}`。
**特征**：`结构：array(N)` 或 `object{...}`，但元素确实是书签节点。

### 3. 扩展版本不匹配
**特征**：报 `schemaVersion=3 高于本扩展支持的 2`。升级扩展即可，不要修文档。

### 4. 文件是空的或被截断
**特征**：`invalid-json`，preview 很短。

## 三、两条修复路径

### A. 自动归一化（优先）

设置页 → **5. 云端文档健康** → **自动归一化**

做的事：

1. 把当前云端内容**逐字节**备份到 `bcs-backup/bad-<时间戳>.json`；
2. 尝试识别结构（裸数组 / Map 对象 / 多包一层 / nodes 为 null）；
3. 归一化后带 `If-Match` 写回（有并发保护）。

能修的情况：第 2 类。修不了会明确告诉你"无法自动修复"并建议走 B。

### B. 用本机重建（最后手段）

设置页 → **5. 云端文档健康** → **用本机重建**

做的事：

1. 同样先备份原始内容；
2. 用**当前这台电脑**的书签树生成一份全新文档；
3. 覆盖云端，并把本地同步基线重置为这份新文档。

⚠️ **另一台设备上独有的书签不会保留**。所以顺序很重要：

~~~
1. 在"书签最全"的那台设备上操作
2. 或者：先在另一台设备「导出当前书签 JSON」留档
3. 确实要保留两边内容 -> 先在另一台设备点「立即同步」（它会试图合并）
   如果那台也报错，就各自导出 JSON，用「导入」逐个并进来
~~~

## 四、还有一条路：从 git 历史恢复（GitHub 后端）

GitHub 模式下每次同步都是一个 commit，比任何修复手段都可靠：

~~~bash
git log --oneline -- bookmarks.json        # 找到最后一次正常的
git show <sha> -- bookmarks.json | head    # 确认内容
~~~

然后在扩展里：设置页 → 6. 历史快照与恢复 → 选那个 commit → **合并恢复**。

这条路不会删掉当前设备上新增的书签，只把差异补回来。

## 五、预防

- **不要**把 `bookmarks.json` 当普通文件放进别的同步工具（OneDrive / Dropbox / Syncthing）；
- 用 GitHub 后端时给仓库开分支保护意义不大，但可以在本地留一份 `npm run verify` 的 CI（见 docs/CI.md）；
- 定期点「立即创建快照」，本地和云端各留一份。

## 六、修好之后

点「立即同步」。如果仍然报错：

1. 再去「检查云端文档」看结构有没有变化；
2. 看「8. 运行日志」里的最后几条；
3. 最后手段：设置页 → 「重置同步基线」（不删书签，只丢弃"上次同步结果"的记忆，下次全量重新比较）。
